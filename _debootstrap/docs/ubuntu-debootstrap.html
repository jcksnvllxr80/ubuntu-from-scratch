From-Archive Build

Skip the installer.
Build the rootfs.

Build an Ubuntu 26.04 LTS (Resolute Raccoon) server image straight from the archive. debootstrap pulls base packages, unpacks them into a directory, and a chroot finishes the system. No ISO download, no Subiquity, no "Continue with autoinstall?" prompt — just a bootable raw disk image produced in one script. The tradeoff: you own partitioning, bootloader install, and machine-id hygiene. This guide covers all of it.

Pipeline

01 — BUILD
debootstrap
Partition a raw image. Bootstrap a rootfs. Run chroot steps. Install GRUB.
02 — SYSPREP
Reset state
Wipe SSH host keys, machine-id, logs. firstboot regenerates them per-clone.
03 — STORE
Compress
virt-sparsify → xz. Publish with a sha256. One artifact for all targets.
04 — DEPLOY
dd / iPXE
Stream the compressed image to target disk. firstboot individualizes it on boot.

Why debootstrap

The autoinstall path rides on Canonical's installer: you boot the live-server ISO, Subiquity/curtin read your user-data, and carve up the disk. Simple, but it downloads a ~2 GB ISO you mostly discard and spends 10–20 minutes of Subiquity time every rebuild.

debootstrap walks around the installer entirely — base packages come straight from the archive, unpacked directly. Rebuilds drop to ~3–5 minutes from clean.

TRADE-OFF You own partitioning, bootloader install, initramfs generation, user creation, network config, and machine-id hygiene. Subiquity normally does these for free. build.sh bundles them into one script.

What build.sh does

1. Sparse raw image + GPT partition table

build.sh
truncate -s 8G build/ubuntu.img
parted -s build/ubuntu.img mklabel gpt \
  mkpart ESP  fat32 1MiB 513MiB  set 1 esp on \
  mkpart root ext4  513MiB 100%

Sparse = on-disk size stays tiny until blocks are written. 8 GiB is plenty for a minimal server. 512 MiB ESP is oversized for one bootloader, but leaves room for a second kernel or alternative loader.

2. Loop-mount, format, mount

build.sh
LOOP=$(losetup --find --show --partscan build/ubuntu.img)
mkfs.vfat -F32 -n ESP  "${LOOP}p1"
mkfs.ext4 -L root      "${LOOP}p2"
mount "${LOOP}p2" /mnt/ufs
mount "${LOOP}p1" /mnt/ufs/boot/efi

Labels matter — fstab references them, so the image boots regardless of the device name the target firmware assigns (/dev/sda2, /dev/nvme0n1p2, etc.).

3. Bootstrap

build.sh
debootstrap --variant=minbase \
  --include=linux-generic,grub-efi-amd64,shim-signed,openssh-server,... \
  resolute /mnt/ufs http://archive.ubuntu.com/ubuntu

--variant=minbase yields a ~150 MB rootfs (no Priority: important packages). --include= adds the kernel, bootloader, and everything from config/packages.list in one pass.

4. Bind pseudo-filesystems

build.sh
for d in dev dev/pts proc sys run; do
  mount --rbind /$d /mnt/ufs/$d
  mount --make-rslave /mnt/ufs/$d
done

Without these, kernel postinst scripts can't build initramfs, grub-install can't probe the ESP, and systemd presets don't apply. --make-rslave stops unmount propagation from nuking the host's mounts on teardown.

5. Config files

  • /etc/hostname, /etc/hosts, /etc/fstab (LABEL=root, LABEL=ESP)
  • /etc/netplan/01-netcfg.yaml from config/netplan.yaml
  • /etc/apt/sources.list — main + updates + security
  • /usr/local/sbin/firstboot.sh + /etc/systemd/system/firstboot.service
  • Empty /etc/machine-id so it regenerates on first boot

6. Finish inside the chroot

build.sh
chroot /mnt/ufs /bin/bash <<'CHROOT'
useradd -m -s /bin/bash -G sudo ubuntu
echo ubuntu:ubuntu | chpasswd
passwd -l root
systemctl enable ssh systemd-networkd firstboot.service
apt-get purge -y snapd ubuntu-advantage-tools
grub-install --target=x86_64-efi --efi-directory=/boot/efi \
  --bootloader-id=ubuntu --removable --no-nvram
update-grub
CHROOT
WHY --removable It writes /EFI/BOOT/BOOTX64.EFI — the path EFI firmware searches when no NVRAM entry exists. That's what makes the image portable: it boots on any EFI firmware without needing the firmware's boot order to be populated first.

First boot

firstboot.service is Type=oneshot with ConditionPathExists=!/etc/firstboot-complete. On the first real boot it:

  • Regenerates /etc/machine-id (debootstrap left it empty)
  • Regenerates SSH host keys (unique fingerprint per clone)
  • Drops /etc/firstboot-complete as proof
  • Disables itself
WHY IT MATTERS If you dd one image to 100 servers, each must end up with its own SSH host keys and machine-id. Skipping this step = 100 hosts sharing an identity.

Sysprep before you clone

Before snapshotting the running VM for distribution:

inside the VM
sudo rm -f /etc/ssh/ssh_host_*
sudo rm -rf /var/log/journal/*
sudo truncate -s 0 /etc/machine-id
sudo rm -rf /tmp/* /var/tmp/*
sudo apt-get clean
sudo shutdown -h now        # halt, do NOT reboot

Compress & store

host
sudo virt-sparsify --compress build/ubuntu.img build/ubuntu.sparse.img
xz -T0 -9 build/ubuntu.sparse.img
sha256sum build/ubuntu.sparse.img.xz > build/ubuntu.sparse.img.xz.sha256

An 8 GiB raw with ~1.5 GiB used typically lands at 300–500 MB compressed. Publish that + its sha256.

Deploy to bare metal

host
xzcat ubuntu.sparse.img.xz | ssh root@target \
  'dd of=/dev/nvme0n1 bs=8M status=progress'

Or serve the image over HTTPS and boot the target via iPXE into a rescue shell that wgets + pipes into dd. Either way, firstboot.service takes over on first boot.
